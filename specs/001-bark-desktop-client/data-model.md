# Phase 1 Data Model — Bark Desktop Client

Storage: SQLite (`data/bark.db`, WAL) for structured state; `data/settings.json` for preferences; `data/identity.bin` (DPAPI-encrypted) for activation secrets; `data/images/` for cached images; `data/logs/` for diagnostics.

Design rules applied throughout:
- One device identity and one Bark link per installation; both are singletons enforced by `CHECK (id = 1)`.
- Secrets never enter the database. Only a certificate fingerprint and non-secret identifiers are stored there.
- Every timestamp is stored as UTC epoch milliseconds; display converts to local time.
- Retention and eviction are expressed as SQL/file operations that can run on the receiver thread.

## DeviceIdentity (singleton)

The anonymously activated emulated Apple device.

| Field | Type | Notes |
|-------|------|-------|
| `id` | integer | Always `1` |
| `udid` | text | Generated UUID v4 at activation; stable across restarts |
| `serial` | text | Generated at activation; stable |
| `device_class` | text | Fixed `Windows` for the activation request |
| `cert_fingerprint` | text | SHA-256 of the DER certificate; identifies the cached secret blob |
| `state` | text | `absent` \| `activating` \| `active` \| `invalid` |
| `activated_at` | integer | When activation succeeded |
| `last_used_at` | integer | Last successful courier connect |
| `last_error` | text | Last activation/connect failure, redacted |

**Secret blob** (`data/identity.bin`, DPAPI): `{cert_pem, key_pem, udid, serial, base_token_hex}`. The row is only valid while `cert_fingerprint` matches the blob's certificate.

**State transitions**
- `absent` → `activating` (setup or first launch)
- `activating` → `active` (activation returns a certificate + token)
- `activating` → `invalid` (activation error; partial material discarded)
- `active` → `invalid` (courier rejects the certificate or token repeatedly)
- `invalid` → `activating` (user-triggered retry; must be rate-limited to one attempt / 60 s)
- `active` → `active` (token refresh on reconnect when `ConnectAck` returns a new token)

**Validation**
- `udid`/`serial` are generated once and reused; regenerating them must produce a new identity row, not a mutation.
- Cached activation is reused indefinitely while connects succeed; activation is not repeated on ordinary restarts.
- A new activation must overwrite the blob only after success (write temp + atomic replace), so a crash cannot leave a half-written identity.

## BarkLink (singleton, active)

The binding between this device and a Bark-compatible server.

| Field | Type | Notes |
|-------|------|-------|
| `id` | integer | Always `1` |
| `server_url` | text | Normalized: scheme + host [+ port] [+ path prefix], no trailing slash; `https` default |
| `device_key` | text | Server-issued key; generated by the server when we register without one |
| `push_topic` | text | Default `me.fin.bark`; advanced override for forked servers |
| `state` | text | `unlinked` \| `registering` \| `linked` \| `stale` \| `abandoned` |
| `created_at` / `updated_at` | integer | Lifecycle timestamps |
| `last_verified_at` | integer | Last successful `GET /register/{key}` |
| `last_error` | text | Last server failure, redacted |

**State transitions**
- `unlinked` → `registering` (user picks a server, activation succeeded)
- `registering` → `linked` (server returned a key)
- `registering` → `stale` (network failure, 4xx/5xx, token rejected) — the previous `linked` row is preserved until the new one succeeds
- `linked` → `stale` (periodic key check fails)
- `stale` → `registering` (retry / different address)
- `linked` → `abandoned` (user switches servers; the key cannot be deleted server-side — UI states this explicitly)

**Validation**
- `device_key` must be non-empty, ≤ 160 chars, and URL-safe before use in links/QR.
- `server_url` must be `http(s)://` and must not contain credentials; `http` requires explicit user confirmation.
- Re-registering the same `device_key` replaces that key's token mapping (server-side overwrite), which is how rotation is achieved.
- Switching servers to a *different* host marks the old link `abandoned` and records `abandoned_at`; the app never claims the old key was revoked.

**Derived values (not stored)**
- Push URL: `{server_url}/{device_key}`
- Share/QR payload: `{server_url}/{device_key}` (a real push endpoint, so scanning or pasting it is directly usable by senders)

## Notification

A message received while the app was connected. Notifications are never synthesized or imported (spec: no backfill).

| Field | Type | Notes |
|-------|------|-------|
| `id` | integer PK | Local id; used by the UI and detail view |
| `remote_id` | text null | Bark `id` field; used for delete/recall and collapse |
| `title` | text | May be empty (silent/empty-alert pushes are ignored) |
| `subtitle` | text null | Merged into title for display |
| `body` | text | Plain text; markdown is not rendered in v1 |
| `group_name` | text null | From custom `group` or `aps.thread-id` |
| `url` | text null | Click-through target; must be `http(s)` to be opened |
| `level` | text null | `active`, `timeSensitive`, `passive`, `critical`; stored only |
| `image_url` | text null | From custom `icon` or markdown image extraction |
| `image_id` | integer null | FK → ImageCache (nullable) |
| `raw_json` | text | Original payload (≤ 4 KB) for forward compatibility |
| `received_at` | integer | Local arrival time (UTC ms) |
| `read_at` | integer null | Null = unread |
| `deleted_at` | integer null | Soft delete for recall; hard-deleted by retention |
| `source_server` | text | Host that delivered it, for multi-server history clarity |

**Validation and behavior**
- Unique index on `(source_server, remote_id)` where `remote_id IS NOT NULL`; duplicates are ignored, so redelivery cannot create double entries.
- Pushes with no title, no body, and no subtitle are recorded as raw-only debug rows only if a `delete` flag is absent; otherwise ignored.
- `delete = 1` removes the row matching `remote_id` (soft delete → immediate hard delete) and dismisses its toast if still visible.
- Body length is capped at 8 KB of stored text (payload maximum is 4 KB, so this is a safety net); toast text is truncated at 200 characters per line.
- Unread count = `COUNT(*) WHERE read_at IS NULL AND deleted_at IS NULL`.

## ImageCache

Content store for notification images, addressed by URL hash.

| Field | Type | Notes |
|-------|------|-------|
| `id` | integer PK | Referenced by `Notification.image_id` |
| `url_hash` | text unique | SHA-256 of the normalized URL |
| `url` | text | Original URL |
| `path` | text | Relative path under `data/images/` |
| `bytes` | integer | Size on disk |
| `width` / `height` | integer | Decoded dimensions |
| `thumb_path` | text | 320 px-wide preview used in lists |
| `state` | text | `pending` \| `cached` \| `unavailable` \| `too_large` \| `not_image` |
| `fetched_at` | integer | |
| `last_used_at` | integer | Drives LRU eviction |

**State transitions**: `pending` → `cached` (valid image), or `pending` → `unavailable` / `too_large` / `not_image` (terminal until the URL changes). A failed fetch never blocks the notification; the entry renders with an unavailable-image placeholder.

**Eviction**: while `SUM(bytes) > 200 MB`, delete the least-recently-used `cached` rows and their files (never delete files referenced by notifications still inside retention).

## Settings (`data/settings.json`)

| Key | Default | Validation |
|-----|---------|------------|
| `server_url` | `https://api.day.app` | URL rules above |
| `push_topic` | `me.fin.bark` | Non-empty, ≤ 155 chars |
| `history_retention_count` | `500` | 50–10 000 |
| `history_retention_days` | `30` | 1–365 |
| `image_cache_mb` | `200` | 20–2 000 |
| `toasts_enabled` | `true` | bool |
| `hide_preview_text` | `false` | bool (renders "New notification" instead of title/body) |
| `tts_enabled` | `false` | bool; read new notifications aloud |
| `tts_provider` | `windows` | `windows` (SAPI 5, no extra dependency) \| `none` |
| `tts_include_body` | `true` | bool; title only when false |
| `tts_rate` | `0` | -10–10 (SAPI rate) |
| `tts_volume` | `100` | 0–100 |
| `tts_max_chars` | `300` | 40–1 000; spoken text is clipped on a word boundary |
| `silence_until` | `null` | UTC ms; temporary do-not-disturb while still recording |
| `autostart_enabled` | `false` | bool; mirrors the HKCU Run entry |
| `autostart_path` | `null` | Path written to the Run entry, for stale-path detection |
| `launch_at_login_configured_at` | `null` | Timestamp of last autostart write |
| `last_connected_at` | `null` | UTC ms, shown in the UI (supports the "you may have missed messages" message) |
| `message_route` | `realtime` | `realtime` \| `bark` \| `both`; destination of compose-bar messages |
| `message_route_url` | `""` | http(s) Bark push URL including the device key; optional query; used by the `bark`/`both` routes |
| `log_level` | `info` | `debug` \| `info` \| `warning` |

Settings are written atomically (temp + replace) and validated on load; invalid values fall back to defaults with a log entry rather than failing startup.

## ConnectionStatus (in-memory, not persisted)

| State | Tray rendering | Meaning |
|-------|----------------|---------|
| `starting` | grey | Process up, receiver not yet running |
| `connecting` | amber | Activation/registration/courier connect in progress |
| `active` | normal + unread badge | Stream open, acks flowing |
| `degraded` | amber + `!` | Reconnecting after network loss, sleep, or keepalive failure |
| `invalid` | red + `!` | Activation or link rejected; user action required |
| `silenced` | normal + moon | Toast suppression active; messages still recorded |

`last_connected_at` is persisted on every transition into `active`, so the UI can say "last connected 3 hours ago — messages sent since then were not received".

## Entity relationships

```text
DeviceIdentity (1) ──activated-for──> BarkLink (1) ──registers-token-with──> external Bark server
Notification (N) ──image_id──> ImageCache (0..1)
Notification (N) ──received while──> ConnectionStatus (transient)
Settings (1) ──references──> BarkLink.server_url, DeviceIdentity (implicitly)
```

## Retention and lifecycle summary

- Notifications: hard-delete when older than `history_retention_days` or beyond the newest `history_retention_count`, whichever is stricter; run at startup and then hourly.
- Images: LRU-evict to `image_cache_mb`; purge files with no notification reference older than 7 days.
- Logs: rotate 2 MB × 3.
- Full local wipe: remove `data/identity.bin`, `data/bark.db`, `data/images/`, `data/logs/`, `data/settings.json`, plus the autostart entry and `barkpc:` registration; documented as the "Remove all data" action.
